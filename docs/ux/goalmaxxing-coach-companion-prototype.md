# Companion: a continuous coach experience

Interactive reference: `/prototype/coach`, behind the moderator-only UX lab gate.
This is an unlisted, noindex frontend
study with fixed sample data for Friday, October 2, 2026. It makes no coach,
planner, or digest API calls. It does not replace the production AppShell or the
existing coach. Refresh or Reset clears the sample state. Responses are scripted,
not generated by an LLM.

## The interaction contract

The companion belongs to the application shell. It has three sizes: a compact
presence, a pane alongside the current work, and an expanded workspace containing
rooms. Expansion changes the size of the same surface; it does not navigate away
or start a new conversation. Contracting reveals the original page and selection.
The app destination controls remain reachable while the coach is expanded.

Desktop uses a companion beside the page and a wider room workspace. Phone uses
a lower sheet that expands below the app navigation. The same conversation,
draft, room, and pending reply survive these changes. Motion explains continuity;
reduced-motion preferences remove the transitions. Escape contracts one level,
and Command/Ctrl J toggles the companion. Focus returns to the launcher when
minimized and to the composer when opening a conversation.

The context bar exposes the current page and purpose, selected work, today's
completion counts, this week's counts, and sample data revision. Marking work
complete in the page or check-in and applying a reviewed move update the same
sample planner model. Every room sees those updated facts. Historical messages
label their context as a snapshot at send time.

Rooms group ongoing intentions, linked goals, confirmed preferences, and separate
conversations. Conversations have their own drafts. A pending reply lands in its
original conversation even if the user switches rooms or minimizes the coach.
New rooms and conversations are functional. Room understanding can be edited;
rooms can be archived and restored without deleting history.

The Understanding view distinguishes editable intentions and confirmed user
preferences from current facts derived from linked goals. Saying “remember…”
proposes storing the exact user text; confirmation is separate from sending the
message. Forget removes the preference. Remembering never changes the schedule.

Daily and weekly check-ins live inside the companion with Recap and Next views.
They share current plan facts. Recap allows recording previously completed work
inline. Talk this through opens a conversation in the current room. This study
does not model automatic cadence, presentation eligibility, monthly check-ins,
or digest generation; those remain responsibilities of the existing digest system.

Changes are reviewed as exact before/after placements. Apply updates the sample
planner; Dismiss leaves it unchanged; Undo restores an applicable placement.
Any intervening planner edit makes an outstanding proposal stale and requires
refresh before application. The Changes view keeps proposals and receipts across
rooms. Actual production mutations must continue using canonical server writes.

## Walkthrough

1. Start beside Plan. Ask **Make today lighter**. Apply the proposed writing move.
   Minimize the coach and see the session move to Saturday. Reopen and undo it.
2. Ask for another move. Complete Strength in Plan before applying the proposal.
   The proposal now requests refresh against the current data revision.
3. Expand. Open **A writing practice**, switch between its existing conversations,
   and start a fresh conversation. Write a draft, switch rooms, and return.
4. Ask **Remember: mornings are my clearest time**. Confirm it and inspect
   Understanding. Edit the room's intention or goal links and save. Forget a
   preference. Create a room, archive it, and restore it from archived rooms.
5. Open Check-in. Record yesterday's reading in Daily Recap, then Talk this
   through. Switch to Weekly and compare Recap with Next.
6. Change destinations to Progress, Community, or You. Select work in Plan or
   Progress. Open the context bar to see the page purpose and current selection.
7. Use the phone control in the prototype toolbar. Expand and contract without
   losing the conversation. Try offline sending, reconnect, and send the retained
   draft. Stop a pending reply while keeping the next draft intact.

The book control in the toolbar includes a shorter walkthrough in the prototype.

## Ownership and production wiring

`src/features/coach-prototype/model.ts` is the single local sample state and
deterministic response model. `use-prototype.ts` owns the simulated response
lifecycle. Components own presentation and local controls. The route imports
only the prototype; there is no mutation adapter into production services.

Use this as an interaction reference for the central-coach frontend work. Do not
promote the sample reducer or scripted replies into production business logic.
The production integration should:

- Mount one shell-level companion; size and selected view are presentation state.
- Reuse central-coach topics, threads, drafts, run lifecycle, memory, and action
  contracts instead of introducing a parallel coach data model.
- Publish page purpose and selected entity from each owning destination. Derive
  today/week facts on the server from authoritative data; refresh when canonical
  mutations or another device change it.
- Preserve the active room, thread, draft, scroll position, and originating page
  during expansion. Keep pending runs associated with their original thread.
- Render existing digest facts and generation in this surface, including existing
  cadence and presentation rules; hand questions into the selected conversation.
- Route action approval and undo through existing server transactions. Use the
  server's revision/conflict receipts rather than the prototype's local counter.
- Keep confirmed memory distinct from current domain facts, with visible sources
  and deletion controls.

Written coverage exercises continuity, contextual facts, stale proposal review,
apply/undo, memory confirmation, linked goals, and delayed response delivery.
No tests, typecheck, lint, browser verification, or CI were run for this prototype.
